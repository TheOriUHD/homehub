# caddy-reader — vendoring export

A self-contained copy of the `caddy-reader` helper, so an application other than
devtracker can build it, serve it, and offer its installation the same way.

This is the **shipping source**, not a reproduction: the `.go` files are byte-for-byte
what devtracker builds, except for two corrected stale comments (§13 of
[CLIENT-NOTES.md](CLIENT-NOTES.md)) and a neutral `go.mod` module path.

**Nothing here contains a secret.** No token, no pairing file, no host-specific
path. The one token-shaped string in the tree is the literal
`REPLACE_ME_64_HEX_CHARS_FROM_CRYPTO_RAND` in `templates/caddy-reader.env`, which
is a placeholder — the real token is generated by `crypto/rand` on the target
machine during `caddy-reader setup` and never leaves it. No secret is embedded at
build time either; the only `-ldflags -X` is the version string.

## The templates are generated, not transcribed

`setup.go` builds the unit file and the env file in code. Copying them into a
document by hand creates a second source of truth that is wrong the first time
someone edits the Go.

So the four files in `templates/` were produced by **calling `unitFile()` and
`envFileText()` directly** and writing the result. They are exactly what
`caddy-reader setup` writes, with the token replaced by a placeholder and the
detected values replaced by their defaults.

They are there to be **read** — so you can review what lands on the Caddy host
before it does, and so a reviewer can compare the two sandbox profiles side by
side. `setup` writes them itself; nothing needs to ship them.

| File | When setup writes it |
|---|---|
| `caddy-reader.service.readonly` | default — `DynamicUser`, `ProtectSystem=strict`, `ReadOnlyPaths=/`, empty `CapabilityBoundingSet` |
| `caddy-reader.service.writable` | `--writable` — `User=root`, `ProtectSystem=full`, `ReadWritePaths=/etc/caddy` |
| `caddy-reader.service.readonly.with-caddy-env` | when Caddy's own unit has `EnvironmentFile=` entries; each is added as `EnvironmentFile=-<path>` (optional). Shown as a third file only to make the difference visible — it is not a third mode. |
| `caddy-reader.env` | always, mode `0600` |

The difference between the two sandboxes is the entire security story of write
mode, and it is worth reading both before deciding to enable it.

## Getting to a working install

```bash
# 1. build
cd src && ./build.sh release          # → dist/caddy-reader-linux-{amd64,arm64,armv7} + SHA256SUMS

# 2. serve  (see serve/URL-PATHS.md)
#    GET /helper/install.sh                → serve/install.sh with __BASE_URL__
#                                            replaced by the request's own origin
#    GET /helper/caddy-reader-linux-<arch> → the binaries
#    GET /helper/SHA256SUMS                → the checksums

# 3. the operator, on the Caddy host
curl -fsSL http://<your-app>/helper/install.sh | sudo bash
sudo caddy-reader setup               # wizard; ends by printing a six-digit code

# 4. your app: POST {baseUrl}/pair {"code":"481502"} → {"token": "…"}
#    store the token encrypted; it is the only credential
```

Step 3's `setup` asks four questions, all pre-filled from the running Caddy
service, and the fourth is the one that matters: *may this app change your
sites?* Read-only is the default and needs no privileges at all.

## What to read, in what order

1. **`src/main.go`** — the whole HTTP surface, and the two constants that make
   "can this write to Caddy?" answerable by inspection.
2. **`src/projection.go`** — the allowlist. Short, and the reason a client can be
   trusted with the output.
3. **`fixtures/README.md`** — then write those two tests before writing your
   parser, not after.
4. **`CLIENT-NOTES.md`** — before writing the client. It is the list of things
   that will otherwise cost you an afternoon.
5. **`BUILD.md`** — when you get to shipping binaries.

## Three things not to change

**Do not expose Caddy's admin API.** The helper exists so `127.0.0.1:2019` can
stay on loopback. Nothing in this system, and nothing in its documentation,
should ever suggest `admin 0.0.0.0:2019` — that turns a reverse proxy into an
open control plane for the whole LAN.

**Do not adapt the Caddyfile client-side.** Post the **text** with
`Content-Type: text/caddyfile` and let Caddy adapt it in its own process. A
config containing `{env.CLOUDFLARE_API_TOKEN}` adapted anywhere else produces
JSON with an *empty* token, and Caddy then rejects it as **invalid** rather than
missing — an error message (`API token "" appears invalid`) that sends you
looking at Cloudflare instead of at your own environment.

**Do not validate after writing.** Post to Caddy first; only touch the disk once
Caddy has accepted. A refused config then never reaches the filesystem, so there
is nothing to roll back and no window in which the file and the running proxy
disagree.
